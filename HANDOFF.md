# ezCLI — cross-agent handoff

This file lets work continue across assistants (Claude ⇄ Codex) and across
sessions. **Whoever picks up work reads this top to bottom first, then updates
the "Current status" and "Session log" sections before handing back.**

## 0. What ezCLI is

A fast, native desktop GUI that runs AI coding CLIs (Claude Code, Claude, Codex,
ChatGPT) each in a real pseudo-terminal. It is **not a harness**: keystrokes go
straight to the PTY, nothing is injected, no model call originates from ezCLI
itself. UI is modeled on the Freebuff desktop shell (near-black chrome, lime
brand accent).

## 1. Architecture (as of v1.1.0)

**Rust + Tauri 2** backend, vanilla HTML/CSS/JS frontend over Tauri IPC.
There is **no Node runtime, no Electron, no bundler.** Electron was deliberately
removed at the user's request ("rebuild in rust and not electron vibe coded
mess"). Do not reintroduce Electron.

```

                        tauri-plugin-dialog, tauri-plugin-opener
```

### Key frontend facts
- `const T = window.__TAURI__;` — `invoke = T.core.invoke`, `listen = T.event.listen`.
- Preferences persist to `localStorage['ezcli.v2']` (see `DEFAULT_PREFS`).
- Sessions persist across restarts as `prefs.parked` snapshots → rebuilt as
  **parked** tabs on boot → Resume button calls `launch(s)`.
- App-owned shortcuts are **Ctrl+Alt** only (`isAppShortcut`), so the CLI's own
  keys (Ctrl+C/W/R, Ctrl+1…) are never shadowed.
- Launch args come ONLY from agents.json, never the frontend (security).

### Key backend facts
- `agents.json` entries: `{id,label,vendor,icon,command,args,modes[],models[]}`.
  `modes`/`models` each have `{id,label,args[]}` appended to the launch line.
- `default_start_dir()` returns the user's home unless cwd is clearly inside it
  (fixes the "opens in C:\Program Files\ezCLI" bug).
- PTY: `.ps1` shims are run via `powershell.exe -File`; everything else direct.

## 2. Build & release

**Local builds do NOT work on this machine.** Rust is installed (GNU default
toolchain) but the self-contained mingw lacks `as.exe`, so `windows-sys` fails
to link. MSVC Build Tools would fix it but aren't installed.

**CI is the build path.** Push a `v*` tag → `.github/workflows/release.yml`
runs on `windows-latest` (real MSVC), builds `cargo tauri build --bundles msi`,
attaches the MSI to the release. ~8–10 min (the workflow was updated on `main`
to download the prebuilt Tauri CLI, shaving ~5 min — but a tagged build uses the
workflow *at that tag*, so the speedup applies from the next tag cut after
40e19a5).

Release a new version:
1. bump `version` in `src-tauri/tauri.conf.json` AND `src-tauri/Cargo.toml`
2. commit, `git tag vX.Y.Z && git push origin vX.Y.Z`
3. watch: `gh run watch <id> --exit-status`
4. verify: `gh release view vX.Y.Z --json assets`

`gh` is authed as Aryansingh0783. Node 24 + npm are available for tooling
(e.g. `node -c file.js` to parse-check) but are NOT part of the app.

## Handoff protocol (READ THIS)

The point of this protocol is to survive an **abrupt cutoff** (usage runs out
mid-PR, no chance to write a goodbye). Three safety nets make that recoverable:

1. **The working tree on disk is the ground truth.** A cutoff ends the
   assistant's session, not the files in `F:\WORK\cli-gui`. Half-written code is
   still there — `git status` + `git diff` show every uncommitted line.
2. **§5 is updated BEFORE and DURING work, committed, not just at the end.**
3. **Commit small and often**, so `git log` narrates what already landed.

**Before you START a PR (or a meaningful chunk):**
1. Set **§5** to `IN PROGRESS — PR n`, list the files you're about to touch and
   the first concrete step. Commit just this file:
   `git commit -m "handoff: start PR n"`.

**At each checkpoint while working (every ~30–60 min or per sub-step):**
1. Commit code progress with a clear message (WIP commits are fine:
   `WIP PR n: <what works, what's stubbed>`).
2. Refresh **§5** with done / half-done / next, and commit it.

**When you stop gracefully:**
1. Finalize **§5** (branch, what's done, what's half-done, exact next step).
2. Append a line to **§6 Session log**.
3. If uncommitted work remains, either commit it as `WIP` or say in §5 exactly
   what's on disk and why it isn't committed.
4. Commit this file. Do NOT add co-author/attribution lines.

**When you PICK UP work (abrupt cutoff or not):**
1. Read this whole file.
2. `git log --oneline -15`, then `git status`, then `git diff` — reconcile the
   real tree against §5. If §5 says "IN PROGRESS PR n" and `git diff` shows
   half-written files, resume those; the diff IS the state.
3. If a WIP commit is the last thing, continue from there. Keep PRs small.
